# Example output

Every file in this folder is **real output from Atlas AI's pipeline**,
not hand-written to look good. It's generated directly from the actual
Pydantic fixture objects in `app/demo/seed_data.py` — the same objects
`MockLLMProvider` returns to the agents at runtime — via a small script,
so what you're looking at is byte-identical to what the running system
produces for the prompt:

> "Build a customer revenue pipeline from raw Stripe and Postgres events"

This is demo-mode output (deterministic fixtures, not a live Groq call),
because that's what's reproducible and inspectable without API keys. The
pipeline structure, validation logic, and DataHub grounding are real
regardless of mode — see `_pipeline_output.json` for the full structured
trail (matched datasets with confidence scores, QA checks, writeback
summary) behind these files.

## What's here

| File | What it is | Generated by |
|---|---|---|
| `models/staging/stg_stripe_payments.sql` | dbt staging model, cleans raw Stripe events | Data Engineer |
| `models/staging/stg_postgres_customers.sql` | dbt staging model, cleans Postgres customer records | Data Engineer |
| `models/marts/fct_customer_revenue.sql` | dbt mart model, order-grain revenue fact table joining both sources | Data Engineer |
| `analysis/revenue_by_day.sql` | Ad-hoc SQL query against the mart | Data Engineer |
| `models/marts/schema.yml` | dbt tests — uniqueness, not-null, range checks | Data Engineer |
| `dbt_project.yml` | dbt project config excerpt | Data Engineer |
| `docs/fct_customer_revenue.md` | Data dictionary for the mart table | Documentation |
| `GENERATED_README.md` | Pipeline-authored README for the generated project (note: renamed from `README.md` to avoid colliding with this index) | Documentation |
| `_pipeline_output.json` | Full structured output from Planner, Metadata Analyst, QA, and Writeback — the parts that don't take the shape of a file | all agents |

## Worth noting when evaluating quality

- **`fct_customer_revenue.sql` only references columns that exist** in the
  three source datasets Metadata Analyst matched (`raw.stripe_payments`,
  `public.customers`, `public.orders` — see `_pipeline_output.json`'s
  `metadata_analyst.matched_datasets`) — nothing here is a hallucinated
  column name.
- **The QA agent correctly flagged `card_last4` as unmasked PII** (see
  `_pipeline_output.json`'s `qa.checks`) — this is a genuine deterministic
  check (SQL parsing + DataHub field-description matching in
  `app/agents/qa_agent.py`), not an LLM guess, and it's why this example
  run's overall `passed` is `false` despite every other check passing.
  That's intentional: a real, working validation catch, not a cherry-picked
  clean run.
- **`schema.yml` tests match the actual primary/foreign keys** used in
  `fct_customer_revenue.sql`, not generic placeholder tests.

## Regenerating this folder

```bash
cd backend
source .venv/bin/activate
python3 -c "
import json, os
from app.demo.seed_data import DATA_ENGINEER_OUTPUT, DOCUMENTATION_OUTPUT, QA_OUTPUT, PLANNER_OUTPUT, METADATA_ANALYST_OUTPUT, WRITEBACK_OUTPUT
for f in list(DATA_ENGINEER_OUTPUT.files) + list(DOCUMENTATION_OUTPUT.files):
    path = os.path.join('examples', f.filename)
    os.makedirs(os.path.dirname(path), exist_ok=True)
    open(path, 'w').write(f.content)
"
```

To see real (non-fixture) output instead, run the pipeline in real mode
(`DEMO_MODE=false`, real `GROQ_API_KEY`, real `DATAHUB_GMS_URL`) via
`POST /api/requests` with your own prompt, then pull the result from
`GET /api/requests/{id}/artifacts`.
